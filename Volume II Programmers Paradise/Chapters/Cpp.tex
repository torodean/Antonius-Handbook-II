\idx{C++} is a powerful, high-level programming language renowned for its performance, flexibility, and extensive standard library. Developed by Bjarne Stroustrup in the early 1980s, C++ is an extension of the C programming language with added support for \idx{object-oriented} programming (\idx{OOP}) features, such as \idx{classes}, \idx{inheritance}, and \idx{polymorphism}. C++ is widely used in systems programming, game development, embedded systems, and performance-critical applications due to its close-to-the-metal capabilities and efficient \idx{memory management}. Its rich standard library provides developers with a wide range of functions and data structures for building robust and scalable applications. C++'s versatility allows developers to write code that is both low-level, allowing direct hardware access, and high-level, facilitating complex software design patterns. Despite its complexity, C++ remains a popular choice for developers seeking performance and control over their software projects.

\section{Basics of the Language}

A basic C++ \idx{hello world} program follows. This program includes the <iostream> header file, which provides input and output functionality. The main() function is the entry point of the program, and it simply outputs "Hello, World!" to the console using std::cout, which is the standard output stream. Finally, return 0; indicates successful program execution.

\begin{lstlisting}
#include <iostream>

int main() {
    // Print "Hello, World!" to the console
    std::cout << "Hello, World!" << std::endl;
    return 0;
}
\end{lstlisting}

The C++ main function is designed by default to pass in \idx{arguments} when a program is ran. The argument passing is set up as follows.
\begin{lstlisting}
int main(int argc, char *argv[])
{
	// argc would represent how many arguments were passed to the program.
	// argv[] is an array of each argument with the first element being the program name.
	for (int i=0;i<argc;i++) std::cout << argv[i] << std::endl; //Prints the arguments.
	return 0;
}

// So for example if I had HelloWorld.cpp as the above and ran using
// ./HelloWorld argument1 argument2 argument3
// we would get an output of 
/some/file/path/HelloWorld
argument1
argument2
argument3
\end{lstlisting}

``The \idx{address} of a variable can be obtained by preceding the name of a variable with an \idx{ampersand} sign (\&), known as \idx{address-of} operator. \cite{cpp:pointers}
\begin{lstlisting}
var = 314;       //Creates a variable and stores in in memory.
address = &var;  //Returns the memory address of the stored variable.
\end{lstlisting}

``\idx{Pointers} are said to `point to' the variable whose address they store.'' \cite{cpp:pointers} Proceeding a pointer with the dereference operator (*), which can be read as `value pointed to by' can be used to access a variable which stores the address of another variable (called a \textbf{pointer}).
\begin{lstlisting}
pointer = *address; //Sets pointer to the value of the variable that address points to.
\end{lstlisting}

A pointer must be declared using the type of the data the pointer points to.
\begin{lstlisting}
int * number;          //Creates number to point to an int.
char * character;      //Creates character to point to a char.
double * decimals;     //Creates decimals to point to a double.
int array [20];        //Creates an empty array with 20 elements.
number = &array[2];    //Sets number to point to the third memory slot of array.
cout << *number;       //Prints the value stored in array[2].
\end{lstlisting}

\textbf{Incrementing pointers}. ``When adding one to a pointer, the pointer is made to point to the following element of the same type, and, therefore, the size in bytes of the type it points to is added to the pointer.''
\begin{lstlisting}
char *mychar;   //Creates mychar to point to a char.
short *myshort; //Creates myshort to point to a short.
long *mylong;   //Creates mylong to point to a long.

++mychar;       //Would increment to the next memory slot (sizeof(char) = 1 byte).
++myshort;      //Would increment two memory slots (sizeof(short) = 2 bytes).
++mylong;       //Would increment sizeof(long) bytes: 4 on Windows (LLP64), 8 on most Linux/macOS 64-bit (LP64).

*p++   // same as *(p++): increment pointer, and dereference unincremented address
*++p   // same as *(++p): increment pointer, and dereference incremented address
++*p   // same as ++(*p): dereference pointer, and increment the value it points to
(*p)++ // dereference pointer, and post-increment the value it points to 
\end{lstlisting}

Within C++, you can use operations with \textbf{pointers to functions} which is typically used when calling a function with another function as a parameter. An example follows as \cite{cpp:pointers}:
\begin{lstlisting}
int addition (int a, int b){ return a+b; }
int subtraction (int a, int b){ return a-b; }

int operation (int x, int y, int (*functocall)(int,int)){
	int g;
	g = (*functocall)(x,y);
	return g;
}

int main (){
	int m,n;
	int (*minus)(int,int) = subtraction;  //minus is a pointer to a function that has two parameters of type int.
	
	m = operation (7, 5, addition);
	n = operation (20, m, minus);
	cout << n;
	return 0;
}
\end{lstlisting}

\idx{Templates} can be used for defining classes that support multiple types.

For a class template like this, the out-of-line definition must also appear in the same header (visible at the point of instantiation), not in a separate \texttt{.cpp} file.

};

template<class type>
type className<type>::getMax(){ return a>b ? a:b; }
\end{lstlisting}

\subsection{Class Structures}
In C++ a \idx{Class} is an object that can contain variables and functions all defined within the object to be used in various ways. Classes are instantiated by a \idx{constructor} and torn down by a \idx{destructor}.
\begin{lstlisting}
// This creates a class named ParentClass.
class ParentClass{
	// The public members of a class are accessible to anything outside of the class.
	public:
		ParentClass();  // Constructor for the ParentClass.
		~ParentClass(); // Destructor for the ParentClass.
		int notSoSpecialInt = 13; // Creates an integer.
};

// This creates a class named ChildClass and inherits the public features of another class ParentClass.
class ChildClass : public ParentClass {
	// The public members of a class are accessible to anything outside of the class.
	public:
		// Creates a public method to return notSoSpecialInt.
		int getNotSoSpecialInt() { return notSoSpecialInt; }; 
		// Creates a public method to return secretInt.
		int getSecretInt() { return secretInt; };  
		
	// The protected members of a class are accessible to this class and any class that inherits this one.
	protected:
		void hello();      // Creates a protected method hello() that is not defined.
		
	// The private members of a class are only accessible to this class.
	private:
		int secretInt = 2; // Creates a private integer secretInt.
};

// This defines the hello method within the ChildClass class.
void ChildClass::hello() {
	std::cout << "Hello!" << std::endl;
}



int main() {
	ChildClass child;  // Creates an object of ChildClass named child.
	
	int number = child.secretInt();    // ERROR: This would not work because secretInt is private;
	int number = child.getSecretInt(); // SUCCESS: This works becase getSecretInt() is public.
	return 0;
}
\end{lstlisting}

\subsubsection{Prime Numbers}

A simple brute force method to determines if a number of type long is \idx{prime} or not.
\begin{lstlisting}
bool isPrime(long num) {  
	int c = 0;   //c is a counter for how many numbers can divide evenly into num
	if (num == 0 || num == 1 || num == 4) {
		return false;
	}
	for (long i = 1; i <= ((num + 1) / 2); i++) {
		if (c < 2) {
			if (num % i == 0) {
				c++;
			}
		} else {
			return false;
		}
	}
	return true;
}
\end{lstlisting}

\subsection{Simulate Key Strokes}

\subsubsection{\idx{Key Strokes} on \idx{Windows}}

First the correct files must be included and an event must be setup.
\begin{lstlisting}
#define WINVER 0x0500
#include <windows.h> 

INPUT ip;

ip.type = INPUT_KEYBOARD; // Set up a generic keyboard event.
ip.ki.wScan = 0; // hardware scan code for key.
ip.ki.time = 0;
ip.ki.dwExtraInfo = 0;
\end{lstlisting}

After this, functions can be setup to simulate various keys based on the specific key codes, two examples of such are
\begin{lstlisting}
void space() { 
	// Press the "space" key.
	ip.ki.wVk = VK_SPACE; // virtual-key code for the "space" key.
	ip.ki.dwFlags = 0;    // 0 for key press.
	SendInput(1, &ip, sizeof(INPUT));
	
	// Release the "space" key.
	ip.ki.wVk = VK_SPACE;            // virtual-key code for the "space" key.
	ip.ki.dwFlags = KEYEVENTF_KEYUP; // KEYEVENTF_KEYUP for key release.
	SendInput(1, &ip, sizeof(INPUT));
	Sleep(50);
}

void one() { 
	// Press the "1" key.
	ip.ki.wVk = 0x31;   // virtual-key code for the "1" key.                                          
	ip.ki.dwFlags = 0;  // 0 for key press
	SendInput(1, &ip, sizeof(INPUT));
	
	// Release the "1" key.
	ip.ki.wVk = 0x31;                // virtual-key code for the "1" key.
	ip.ki.dwFlags = KEYEVENTF_KEYUP; // KEYEVENTF_KEYUP for key release.
	SendInput(1, \&ip, sizeof(INPUT));
	Sleep(50);
}
\end{lstlisting}

A similar method can be used to simulate mouse clicks. And example for left click follows
\begin{lstlisting}
void leftclick() {
	INPUT ip={0};
	// left down
	ip.type = INPUT_MOUSE;
	ip.mi.dwFlags = MOUSEEVENTF_LEFTDOWN;
	SendInput(1,&Input,sizeof(INPUT));
	
	// left up
	ZeroMemory(&Input,sizeof(INPUT));
	ip.type = INPUT_MOUSE;
	ip.mi.dwFlags = MOUSEEVENTF_LEFTUP;
	SendInput(1,&Input,sizeof(INPUT));
	Sleep(50);
}
\end{lstlisting}

\subsubsection{Inspecting Dynamic Symbols}

It shows symbols a library provides or requires, marked as \texttt{T} (defined, e.g., functions) or \texttt{U} (undefined, to be resolved by another library). Use with \texttt{grep} to find specific symbols.

\begin{lstlisting}[style=terminalstyle]

\end{lstlisting}

\textbf{Output Example:} If \texttt{U otherLibrary::someClass::someMethod} appears, the library expects \texttt{someMethod} from another library, indicating a dependency. If empty, the symbol is not referenced.

\section{Advanced Coding Features}

C++ allows you to perform \idx{compile-time} evaluation of expressions using \idx{constexpr} functions and variables. This feature enables you to compute values at compile-time rather than \idx{runtime}, providing potential performance benefits and allowing for more flexible code optimization.
\begin{lstlisting}
#include <iostream>

constexpr int fibonacci(int n) {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}

int main() {
    constexpr int fib_10 = fibonacci(10);
    std::cout << "Fibonacci number at position 10: " << fib_10 << std::endl;

    return 0;
}
\end{lstlisting}









\subsubsection{\idx{user-defined} \idx{literals}}


C++ allows you to create \idx{user-defined} \idx{literals}, which are custom suffixes that can be applied to literal values to create objects of \idx{user-defined} types. This feature enables you to create more readable and expressive code by introducing \idx{domain-specific} \idx{literals}.
\begin{lstlisting}
#include <iostream>

// Define a user-defined literal for converting meters to kilometers
constexpr long double operator"" _km(long double meters) {
    return meters / 1000.0;
}

int main() {
    // Use the user-defined literal to convert meters to kilometers
    long double distance = 5000.0_km;

	// Outputs "Distance in kilometers: 5"
    std::cout << "Distance in kilometers: " << distance << std::endl;

    return 0;
}
\end{lstlisting}

When using \idx{user-defined} \idx{literals}, it is up to the user to ensure that the units are consistent throughout the application. For example, the below defines literals that convert between Celsius and Fahrenheit. Each literal both tags a value with its source unit and performs the conversion, so the unit of every quantity is explicit at the point where it is written.
\begin{lstlisting}
#include <iostream>

// Convert a Celsius value to Fahrenheit.
constexpr double operator"" _CtoF(long double celsius) {
    return (celsius * 9.0 / 5.0) + 32.0;
}

// Convert a Fahrenheit value to Celsius.
constexpr double operator"" _FtoC(long double fahrenheit) {
    return (fahrenheit - 32.0) * 5.0 / 9.0;
}

int main() {
    // Convert Celsius values to Fahrenheit.
    constexpr double freezing_point_F = 0.0_CtoF;    // 0 C -> 32 F
    constexpr double boiling_point_F  = 100.0_CtoF;  // 100 C -> 212 F

    std::cout << "Freezing point of water in Fahrenheit: " << freezing_point_F << std::endl;
	// Outputs "Freezing point of water in Fahrenheit: 32"
    std::cout << "Boiling point of water in Fahrenheit: " << boiling_point_F << std::endl;
	// Outputs "Boiling point of water in Fahrenheit: 212"

    // Convert Fahrenheit values to Celsius.
    constexpr double boiling_point_C  = 212.0_FtoC;  // 212 F -> 100 C
    constexpr double body_temp_C      = 98.6_FtoC;   // 98.6 F -> 37 C

    std::cout << "Boiling point of water in Celsius: " << boiling_point_C << std::endl;
	// Outputs "Boiling point of water in Celsius: 100"
    std::cout << "Body temperature in Celsius: " << body_temp_C << std::endl;
	// Outputs "Body temperature in Celsius: 37"

    return 0;
}
\end{lstlisting}








\subsubsection{\idx{templates}}

C++ provides a feature called "\idx{template specialization}," which allows you to provide specialized implementations for specific \idx{template} arguments. Template specialization is particularly useful when you need different behavior for certain template arguments while maintaining a generic implementation for others.
\begin{lstlisting}
#include <iostream>

// Generic template
template <typename T>
struct MyTemplate {
    void print() {
        std::cout << "Generic template: " << typeid(T).name() << std::endl;
    }
};

// Specialized template for int
template <>
struct MyTemplate<int> {
    void print() {
        std::cout << "Specialized template for int" << std::endl;
    }
};

int main() {
    MyTemplate<double> obj1;
    obj1.print(); // Output: Generic template: d

    MyTemplate<int> obj2;
    obj2.print(); // Output: Specialized template for int

    return 0;
}
\end{lstlisting}











\subsubsection{\idx{Function Pointers}}

C++ allows you to define and use "\idx{function pointers}," which are \idx{pointers} that point to functions rather than data. Function pointers enable you to treat functions as first-class citizens, allowing you to pass functions as arguments to other functions, store them in data structures, and call them dynamically at runtime.
\begin{lstlisting}
#include <iostream>

// Function pointer type declaration
typedef int (*Operation)(int, int);

// Function to add two numbers
int add(int a, int b) {
    return a + b;
}

// Function to subtract two numbers
int subtract(int a, int b) {
    return a - b;
}

// Function to perform an operation using function pointer
int perform(Operation op, int a, int b) {
    return op(a, b);
}

int main() {
    // Define function pointers
    Operation addition = &add;
    Operation subtraction = &subtract;

    // Use function pointers to perform operations
    std::cout << "Addition result: " << perform(addition, 5, 3) << std::endl;
    std::cout << "Subtraction result: " << perform(subtraction, 5, 3) << std::endl;

    return 0;
}
\end{lstlisting}














\section{PImpl Idiom (Pointer to Implementation)}

The \idx{PImpl} (Pointer to Implementation) idiom is commonly used in C++ to hide implementation details and minimize the compilation dependencies between an interface and the implementation. It is especially useful when you want to reduce the recompilation cost when modifying the implementation of a class, as it allows you to change the private members of a class without affecting its header file.

The PImpl idiom works by moving the implementation details into a separate class, which is accessed through a pointer in the public class. The pointer is then used to forward method calls to the actual implementation.

\subsection{Example: PImpl Idiom}

Below is an example of how the PImpl idiom can be implemented:

\begin{lstlisting}
#include <memory>
#include <iostream>

// Forward declaration of the implementation class.
class MyClassImpl;

// Public interface of MyClass, which hides the implementation details.
class MyClass {
public:
    MyClass();
    ~MyClass();

    void display() const;

private:
    // Pointer to the implementation (PImpl).
    std::unique_ptr<MyClassImpl> pImpl;
};

// The implementation class (hidden from the public interface).
class MyClassImpl {
public:
    void displayImpl() const {
        std::cout << "Displaying implementation details!" << std::endl;
    }
};

// Constructor initializes the pImpl pointer.
MyClass::MyClass() : pImpl(std::make_unique<MyClassImpl>()) {}

// Destructor ensures proper cleanup of the pImpl pointer.
MyClass::~MyClass() = default;

// Public method that forwards the call to the implementation.
void MyClass::display() const {
    pImpl->displayImpl();
}

int main() {
    MyClass obj;
    obj.display();  // Calls the implementation's display method.
    return 0;
}
\end{lstlisting}

\subsection{Benefits of PImpl}
The PImpl idiom provides several advantages:
\begin{itemize}
    \item \textbf{Reduced Compilation Dependencies}: Changes in the implementation class do not require recompiling the public interface (header file).
    \item \textbf{Binary Compatibility}: The header file remains unchanged, ensuring that the ABI (Application Binary Interface) remains stable across different versions.
    \item \textbf{Encapsulation}: The implementation details are hidden from the user, reducing the exposure of internal data structures and methods.
\end{itemize}

\subsection{Considerations}
\begin{itemize}
    \item \textbf{Pointer Overhead}: The use of a pointer adds an extra level of indirection, which may incur a slight performance penalty, especially when dealing with frequently accessed members.
    \item \textbf{Memory Management}: Proper memory management (e.g., using \idx{std::unique\_ptr}) is necessary to ensure that the implementation class is properly destroyed when the public class goes out of scope.
\end{itemize}











\section{Tag Dispatch}

\idx{Tag dispatch} is a technique used in C++ to implement function overload resolution based on types that are not directly related to the arguments but serve as tags to differentiate between different implementations. It allows for more flexible and efficient generic code by choosing the correct implementation based on type traits or other compile-time conditions.

The basic idea is to define different versions of a function or method, each specialized for a particular "tag" type. The dispatching mechanism is usually done through template specialization or \idx{SFINAE} (Substitution Failure Is Not An Error), where the tag itself is used to determine which function version to call.

\subsection{Example: Tag Dispatch}

\begin{lstlisting}
#include <iostream>
#include <type_traits>

// Tag types that will be used for dispatching.
struct tag_int {};
struct tag_float {};

// General template for the function (does nothing by default).
template <typename T, typename Tag>
void process(T value, Tag tag) {
    std::cout << "Generic processing" << std::endl;
}

// Specialized version of process for integers.
template <>
void process<int, tag_int>(int value, tag_int tag) {
    std::cout << "Processing integer: " << value << std::endl;
}

// Specialized version of process for floats.
template <>
void process<float, tag_float>(float value, tag_float tag) {
    std::cout << "Processing float: " << value << std::endl;
}

int main() {
    int i = 10;
    float f = 3.14f;

    process(i, tag_int{});   // Calls the integer-specific version.
    process(f, tag_float{});  // Calls the float-specific version.
    process(i, tag_float{});  // Calls the generic version.
    
    return 0;
}
\end{lstlisting}

\subsection{Benefits of Tag Dispatch}

Tag dispatch can be particularly useful in the following cases:
\begin{itemize}
    \item \textbf{Specialized Implementations}: Allows different code paths to be chosen based on the type of the argument in a highly flexible and extensible way.
    \item \textbf{Compile-Time Decisions}: The dispatch mechanism enables making decisions at compile time, resulting in more efficient and optimized code by avoiding runtime overhead.
    \item \textbf{Extensibility}: Adding new types or modifying the behavior for specific types requires minimal changes, making the system easy to extend.
\end{itemize}

\subsection{Considerations}
\begin{itemize}
    \item \textbf{Complexity}: While powerful, tag dispatch can make the codebase harder to maintain due to its reliance on template metaprogramming techniques and the need to define specialized versions of functions.
    \item \textbf{Overhead}: In some cases, the number of specialized templates required for dispatching can lead to a larger code size, especially when dealing with many types.
\end{itemize}





\section{Modern C++ Utility Types}
Modern C++ (C++11 and later) introduces several utility types that simplify common programming tasks. These are part of the C++ Standard Library and do not require any external dependencies. They are used across a wide range of applications, from everyday code to library development, and are independent of any specific programming paradigm.

\subsection{std::optional}
Introduced in \idx{C++17}, \idx{std::optional} provides a type-safe way to represent optional values - a value that may or may not exist. This avoids the need for sentinel values such as \texttt{-1}, \texttt{nullptr}, or separate boolean flags. An \texttt{std::optional} either contains a value of the specified type or is empty (represented by \idx{std::nullopt}).
\begin{lstlisting}
#include <optional>
#include <string>

std::optional<std::string> getValue(const std::string& key) {
    if (hasKey(key)) {
        return getValueForKey(key);
    }
    return std::nullopt; // Explicitly indicates no value.
}

// Usage:
auto result = getValue("myKey");
if (result.has_value()) {
    std::cout << *result << std::endl; // dereference to access the value
} else {
    std::cout << "Key not found!" << std::endl;
}
\end{lstlisting}
\idx{std::optional} is commonly used for return values that may not exist (e.g., lookup, parse, file read), avoiding magic sentinel values, and writing safer, more expressive code.

\subsection{std::make\_pair and std::tuple}
\idx{std::make\_pair} (available since \idx{C++11}) and \idx{std::make\_tuple} (available since \idx{C++11}) are utility functions used to construct \idx{pairs} and \idx{tuples} from values. They automatically deduce the element types, making them convenient for bundling multiple values together without defining a custom struct.
\begin{lstlisting}
#include <utility>
#include <tuple>

auto p = std::make_pair("name", 42);          // std::pair<const char*, int>
auto t = std::make_tuple(1, 2.5, "hello");    // std::tuple<int, double, const char*>

// Accessing elements of a pair
std::cout << p.first << ": " << p.second << std::endl;  // name: 42

// Accessing elements of a tuple by index
std::cout << std::get<0>(t) << ", " << std::get<1>(t) << std::endl;  // 1, 2.5
\end{lstlisting}
These utilities are commonly used to store multiple values together (e.g., key-value pairs), return multiple values from a function, and pass multiple arguments to a function or lambda.

\subsection{std::apply}
Introduced in \idx{C++17}, \idx{std::apply} calls a callable object (such as a function or \idx{lambda}) with the elements of a \idx{tuple} as its arguments. While \texttt{std::get<N>()} works fine when you know the tuple's structure at write time, \texttt{std::apply} is essential in generic code where the tuple's size and element types are not known until compile time. A common real-world use case is a task scheduler that stores deferred function calls as tuples of (function, arguments...) and executes them later.
\begin{lstlisting}
#include <iostream>
#include <tuple>
#include <string>

// A generic task executor that receives a tuple of (function, args...).
// At this point, we have NO IDEA what's in the tuple -- how many elements,
// what types, etc. We just know it's a tuple that represents a callable
// and its arguments.
template<typename Tuple>
void executeTask(Tuple&& task) {
    // std::apply unpacks the tuple and calls the function with its args.
    // We couldn't write std::get<0>(task)(std::get<1>(task), std::get<2>(task)...)
    // because we don't know how many arguments there are.
    std::apply([](auto&& func, auto&&... args) {
        func(std::forward<decltype(args)>(args)...);
    }, task);
}

void printSum(int a, int b) {
    std::cout << "Sum: " << a + b << std::endl;
}

void greet(const std::string& name, int times) {
    for (int i = 0; i < times; i++)
        std::cout << "Hello, " << name << "!" << std::endl;
}

int main() {
    // Tasks created elsewhere -- the executor doesn't know their structure
    auto task1 = std::make_tuple(printSum, 3, 4);
    auto task2 = std::make_tuple(greet, std::string("World"), 2);

    executeTask(task1);
    // Output: Sum: 7

    executeTask(task2);
    // Output: Hello, World!
    //         Hello, World!

    return 0;
}
\end{lstlisting}
Notice that \texttt{executeTask} works for both tasks even though they have different numbers of arguments and completely different types. There is no way to write that with \texttt{std::get<N>} because you would need to hardcode the indices, and those indices are different for each task.

\subsection{std::tie}
Introduced in \idx{C++11}, \idx{std::tie} creates a tuple of references from existing variables, allowing a returned \idx{tuple} or \idx{pair} to be unpacked into those variables in a single assignment. It can also be combined with \idx{std::ignore} to discard unwanted elements.
\begin{lstlisting}
std::tuple<bool, int, std::string> getConfig() {
    return {true, 42, "default"};
}

bool ok;
int id;
std::string name;
std::tie(ok, id, name) = getConfig();
// ok = true, id = 42, name = "default"

// Discard the second element
std::tie(ok, std::ignore, name) = getConfig();
\end{lstlisting}
If declaring new variables, C++17 \idx{structured bindings} (\texttt{auto [ok, id, name] = getConfig();}) is generally preferred. \idx{std::tie} remains useful when the variables already exist or when discarding elements with \idx{std::ignore}.

\subsection{std::ignore}
\idx{std::ignore} is a placeholder object that discards a value assigned to it. Its primary use is with \idx{std::tie} to skip elements when unpacking a \idx{tuple} or \idx{pair}.
\begin{lstlisting}
bool ok;
std::string name;
// Discard the int (index 1), keep the bool and string
std::tie(ok, std::ignore, name) = getConfig();
\end{lstlisting}

\subsection{std::variant}
Introduced in \idx{C++17}, \idx{std::variant} provides a type-safe \idx{union}. Unlike a C-style \idx{union}, which provides no way to know which type is currently stored, \idx{std::variant} tracks the active alternative and provides safe access. A mismatched access throws \idx{std::bad\_variant\_access}.
\begin{lstlisting}
std::variant<int, double, std::string> value;

value = 42;
std::cout << std::get<int>(value) << std::endl;       // 42

value = "hello";
if (auto ptr = std::get_if<std::string>(&value)) {
    std::cout << *ptr << std::endl;                   // hello
}
// std::get<int>(value);  // Throws std::bad_variant_access
\end{lstlisting}

\subsection{std::any}
Introduced in \idx{C++17}, \idx{std::any} is a container that can hold a value of any type. Unlike \idx{std::variant}, which requires enumerating all possible types upfront, \idx{std::any} can store any type without advance declaration. The trade-off is that the exact stored type must be known to retrieve the value via \idx{std::any\_cast}, and a mismatched cast throws \idx{std::bad\_any\_cast}.
\begin{lstlisting}
std::any value;

value = 42;
std::cout << std::any_cast<int>(value) << std::endl;      // 42

value = std::string("hello");
std::cout << std::any_cast<std::string>(value) << std::endl;  // hello

// std::any_cast<double>(value);  // Throws std::bad_any_cast
\end{lstlisting}
When the set of possible types is known at compile time, \idx{std::variant} is preferred because it provides compile-time type guarantees. \idx{std::any} is useful when the type set is not known, such as in plugin systems or generic property bags.

\section{Smart Pointers}
C++11 introduced \idx{smart pointers} as part of the \idx{<memory>} header to provide automatic \idx{memory management} and eliminate the need for manual \texttt{new} and \texttt{delete}. Smart pointers use \idx{RAII} (Resource Acquisition Is Initialization) to ensure that memory is freed when the pointer goes out of scope, preventing memory leaks and dangling pointers.

\subsection{std::unique\_ptr}
\idx{std::unique\_ptr} is a smart pointer that has \idx{exclusive ownership} of a dynamically allocated object. Only one \texttt{unique\_ptr} can own the object at a time. Ownership can be transferred using \idx{std::move}, but the pointer cannot be copied.
\begin{lstlisting}
#include <memory>

// Create a unique_ptr
std::unique_ptr<int> p1 = std::make_unique<int>(42);
// std::unique_ptr<int> p2 = p1;  // ERROR: cannot copy

// Transfer ownership
std::unique_ptr<int> p2 = std::move(p1);  // p1 is now nullptr
\end{lstlisting}

\subsection{std::shared\_ptr}
\idx{std::shared\_ptr} is a smart pointer that allows \idx{shared ownership} of a dynamically allocated object. Multiple \texttt{shared\_ptr} objects can point to the same resource. A \idx{reference count} tracks how many \texttt{shared\_ptr} objects own the resource, and the memory is freed only when the last \texttt{shared\_ptr} is destroyed or reset.
\begin{lstlisting}
#include <memory>

// Create a shared_ptr
std::shared_ptr<int> p1 = std::make_shared<int>(42);
std::shared_ptr<int> p2 = p1;  // OK: both share ownership

// Reference count is now 2
std::cout << p1.use_count() << std::endl;  // 2

p1.reset();  // p1 gives up ownership, count drops to 1
// Memory is freed when p2 goes out of scope
\end{lstlisting}

\subsection{std::weak\_ptr}
\idx{std::weak\_ptr} is a smart pointer that holds a \idx{non-owning reference} to an object managed by a \idx{std::shared\_ptr}. It does not participate in the \idx{reference count}, so it cannot prevent the object from being destroyed. To access the object, a \texttt{weak\_ptr} must be converted to a \texttt{shared\_ptr} using \idx{lock()}, which returns a valid \texttt{shared\_ptr} if the object still exists, or an empty one if it has been destroyed.
\begin{lstlisting}
std::shared_ptr<int> shared = std::make_shared<int>(42);
std::weak_ptr<int> weak = shared;  // Does not increase reference count

if (auto locked = weak.lock()) {
    std::cout << *locked << std::endl;  // 42
}

shared.reset();  // Object is destroyed, reference count hits 0

if (auto locked = weak.lock()) {
    std::cout << *locked << std::endl;  // Not reached
} else {
    std::cout << "Object no longer exists" << std::endl;
}
\end{lstlisting}
\idx{std::weak\_ptr} is primarily used to break \idx{reference cycles}. If two objects hold \texttt{shared\_ptr} references to each other, neither will ever be destroyed because each keeps the other's reference count above zero. By making one direction a \texttt{weak\_ptr}, the cycle is broken and both objects can be properly cleaned up.

\subsection{std::make\_unique and std::make\_shared}
\idx{std::make\_unique} (C++14) and \idx{std::make\_shared} (C++11) are factory functions that construct an object and return the appropriate smart pointer. They are preferred over directly using \texttt{new} because they are safer (no raw pointer exposed), more efficient (\texttt{make\_shared} allocates the control block and object in a single allocation), and exception-safe.
\begin{lstlisting}
auto p1 = std::make_unique<int>(42);
auto p2 = std::make_shared<int>(42);

// Prefer this over:
// std::unique_ptr<int> p1(new int(42));
// std::shared_ptr<int> p2(new int(42));
\end{lstlisting}

\section{Type Aliases}
C++ provides two ways to create alternative names for types. \idx{typedef} (inherited from C) and \idx{using} (introduced in \idx{C++11}). The \texttt{using} syntax is preferred in modern C++ because it is more readable and supports \idx{template aliasing}, which \texttt{typedef} cannot do.
\begin{lstlisting}
// typedef syntax
typedef unsigned long ulong;

// using syntax (preferred)
using ulong = unsigned long;

// Template aliasing -- only possible with 'using'
template<typename T>
using StringMap = std::map<std::string, T>;

StringMap<int> ages;  // std::map<std::string, int>
\end{lstlisting}

\section{Range-Based For Loops}
Introduced in \idx{C++11}, \idx{range-based for loops} provide a concise syntax for iterating over containers. C++17 extended this with \idx{structured bindings} in the loop, allowing iteration over \idx{maps} with unpacked key-value pairs.
\begin{lstlisting}
std::vector<int> nums = {1, 2, 3, 4, 5};

// By value (copies each element)
for (int n : nums) { std::cout << n; }          // 12345

// By reference (modifies elements in place)
for (int& n : nums) { n *= 2; }                 // nums is now {2, 4, 6, 8, 10}

// C++17: Structured bindings with a map
std::map<std::string, int> ages = {{"Alice", 30}, {"Bob", 25}};
for (const auto& [name, age] : ages) {
    std::cout << name << ": " << age << " ";
}
// Output: Alice: 30 Bob: 25
\end{lstlisting}

\section{Lambdas}
Introduced in \idx{C++11}, a \idx{lambda} is an anonymous function object that can be defined inline. Lambdas are useful for short functions passed to \idx{STL algorithms}, callbacks, or any situation where defining a named function would be unnecessarily verbose. The general syntax is:
\begin{lstlisting}
[capture](parameters) -> return_type { body }
\end{lstlisting}
The \idx{capture} clause specifies which variables from the enclosing scope are available inside the lambda. The return type is optional and can be deduced by the compiler.
\begin{lstlisting}
#include <algorithm>
#include <vector>

std::vector<int> nums = {5, 2, 8, 1, 9};

// Sort in descending order using a lambda
std::sort(nums.begin(), nums.end(), [](int a, int b) {
    return a > b;
});
// nums is now {9, 8, 5, 2, 1}

// Capture by value
int threshold = 5;
auto above = [threshold](int n) { return n > threshold; };
// above(8) returns true, above(3) returns false

// Capture by reference
int counter = 0;
auto increment = [&counter]() { counter++; };
increment();
increment();
// counter is now 2
\end{lstlisting}
Common capture modes:
\begin{center}
\begin{tabular}{l|l}
Capture & Meaning \\
\hline
\texttt{[]} & Capture nothing \\
\texttt{[=]} & Capture all variables by value \\
\texttt{[\&]} & Capture all variables by reference \\
\texttt{[x]} & Capture \texttt{x} by value \\
\texttt{[\&x]} & Capture \texttt{x} by reference \\
\texttt{[=, \&x]} & Capture all by value, except \texttt{x} by reference \\
\texttt{[\&, x]} & Capture all by reference, except \texttt{x} by value \\
\end{tabular}
\end{center}

\section{Structured Bindings}
Introduced in \idx{C++17}, \idx{structured bindings} allow decomposing an object into its constituent parts in a single declaration. This works with \idx{tuples}, \idx{pairs}, arrays, and simple structs with public members.
\begin{lstlisting}
// Tuples and pairs
auto [success, id, message] = getConfig();

// Maps (unpacks key-value pairs)
std::map<std::string, int> ages = {{"Alice", 30}, {"Bob", 25}};
for (const auto& [name, age] : ages) {
    std::cout << name << ": " << age << std::endl;
}

// Arrays
int arr[3] = {1, 2, 3};
auto [a, b, c] = arr;
\end{lstlisting}








\section{Conditional Compilation with std::enable\_if\_t}
Introduced in \idx{C++14} as a convenience alias for \idx{std::enable\_if::type}, \idx{std::enable\_if\_t} enables or disables a function template overload based on a compile-time condition. This is a cornerstone of \idx{SFINAE} (Substitution Failure Is Not An Error), a C++ rule that allows the compiler to silently ignore a template specialization if a substitution failure occurs during overload resolution, rather than treating it as an error. By leveraging SFINAE, \texttt{std::enable\_if\_t} allows the compiler to select the appropriate overload from a set of candidates based on type traits or other compile-time properties.

In its general form, \texttt{std::enable\_if\_t<Condition, T>} evaluates \texttt{Condition} at compile time. If the condition is \texttt{true}, the expression evaluates to type \texttt{T} (which defaults to \texttt{void} if omitted), and the function template is enabled. If the condition is \texttt{false}, substitution fails and the overload is silently discarded.
\begin{lstlisting}
#include <type_traits>

// Only enabled when T is an integral type (int, long, char, etc.)
template<typename T>
std::enable_if_t<std::is_integral_v<T>, T>
square(T x) {
    return x * x;
}

// Only enabled when T is a floating-point type (float, double, etc.)
template<typename T>
std::enable_if_t<std::is_floating_point_v<T>, T>
square(T x) {
    return x * x;
}
\end{lstlisting}
\idx{std::enable\_if\_t} is commonly used to enable a function only when a condition is met (e.g., argument count, type trait), overload functions based on compile-time properties, and prevent misuse of generic functions.




\section{Variadic Templates and Fold Expressions}
Modern C++ (C++11 and later) provides tools for writing generic, type-safe, and efficient code. Key features include \idx{variadic templates} and \idx{fold expressions}. These are typically used in library development, metaprogramming, and systems code where compile-time flexibility and zero-runtime-overhead abstractions are essential.

\subsection{Variadic Templates}
Introduced in \idx{C++11}, \idx{variadic templates} allow templates to accept any number of type or value parameters. This is accomplished through the use of \idx{parameter packs}, which can represent zero or more types or values. A type parameter pack is declared with \texttt{typename... Args}, while a value parameter pack is declared with \texttt{Args... args}. The \idx{sizeof...} operator returns the number of elements in a parameter pack at compile time.
\begin{lstlisting}
template<typename... Args>
void func(Args... args);

// sizeof...(Args)  returns the number of types in the pack
// sizeof...(args)  returns the number of values in the pack
\end{lstlisting}
Variadic templates are commonly used for functions that take any number of arguments (e.g., logging, formatting, property copying), compile-time checks with \idx{static\_assert} and \idx{sizeof...}, and generic containers or utilities that operate on an arbitrary number of types.

A common metaprogramming pattern using variadic templates is the \idx{type list} - a struct that stores a list of types in its template parameters without holding any data. The type information is accessed at compile time through \idx{partial template specialization}, where utility structs are specialized on \texttt{TypeList<Types...>} and peel types off the pack one at a time through recursion. The following example demonstrates a type list with utilities to query its size and retrieve a type at a specific index.
\begin{lstlisting}
#include <iostream>
#include <typeinfo>

// The type list itself -> just an empty shell that holds type info.
// in its template parameters, not in any data member.
template<typename... Types>
struct TypeList {};

// Compile-time utilities that operate on a TypeList.

// 1. Get the number of types in the list:
template<typename List>
struct Size;

template<typename... Types>
struct Size<TypeList<Types...>> {
    static constexpr size_t value = sizeof...(Types);
};

// 2. Get the Nth type in the list:
template<size_t N, typename List>
struct TypeAt;

// Base case: index 0 returns the first type (Head)
template<typename Head, typename... Tail>
struct TypeAt<0, TypeList<Head, Tail...>> {
    using type = Head;
};

// Recursive case: decrement N and recurse into the remaining types (Tail).
template<size_t N, typename Head, typename... Tail>
struct TypeAt<N, TypeList<Head, Tail...>> {
    using type = typename TypeAt<N - 1, TypeList<Tail...>>::type;
};

// Using it:
using MyTypes = TypeList<int, double, std::string>;

int main() {
    std::cout << "Number of types: " << Size<MyTypes>::value << std::endl;
    // Output: Number of types: 3

    std::cout << "Type at index 1: " << typeid(TypeAt<1, MyTypes>::type).name() << std::endl;
    // Output: Type at index 1: d  (gcc's mangled name for double)

    return 0;
}
\end{lstlisting}
This pattern is used in real libraries. For example, \idx{std::variant} and \idx{std::tuple} internally use similar techniques to store a list of types and generate the appropriate code for each one.

\subsection{Parameter Pack Expansion}
\idx{Parameter pack expansion} expands a parameter pack into multiple arguments using the \texttt{...} syntax. This is fundamental to working with variadic templates, as it allows the pack to be ``unpacked'' into individual arguments when passed to functions, constructors, or other templates.
\begin{lstlisting}
template<typename... Args>
auto makeTuple(Args... args) {
    return std::make_tuple(args...); // args... expands the pack
}
\end{lstlisting}
Parameter pack expansion is commonly used to build \idx{tuples}, arrays, or containers from a pack, pass arguments to functions or constructors, and generate multiple calls or assignments.

\subsection{Fold Expressions}
Introduced in \idx{C++17}, \idx{fold expressions} provide a concise way to apply a binary operator across all elements of a parameter pack at compile time. Prior to C++17, achieving the same result required recursive template instantiation. Fold expressions eliminate this boilerplate and are evaluated entirely at compile time with no runtime cost.
\begin{lstlisting}
// Unary right fold: (pack op ... )
(args && ...)        // true if all args are true

// Unary left fold: (... op pack)
(... + args)         // sum of all args

// Binary fold: (init op ... op pack)
(0 + ... + args)     // sum with explicit initial value
\end{lstlisting}
Fold expressions are commonly used to check if all elements satisfy a condition (e.g., \texttt{\&\&} fold), sum or combine values (e.g., \texttt{+} fold), and call a function on each element of a pack (e.g., with the comma operator). The following example shows a function that returns \texttt{true} only if all boolean arguments are \texttt{true}.
\begin{lstlisting}
template<typename... Args>
bool allTrue(Args... args) {
    return (args && ...); // unary right fold over &&
}
\end{lstlisting}

\subsection{Perfect Forwarding}
Introduced in \idx{C++11}, \idx{perfect forwarding} allows a function template to forward its arguments to another function while preserving the argument's value category (i.e., whether it is an \idx{lvalue} or \idx{rvalue}). This is achieved through \idx{forwarding references} (also known as \idx{universal references}), which are declared using \texttt{T\&\&} in a deduced context, combined with \idx{std::forward} to cast the argument appropriately.
\begin{lstlisting}
template<typename T>
void forwardArg(T&& arg) {
    someFunction(std::forward<T>(arg)); // preserves lvalue/rvalue-ness
}
\end{lstlisting}
Perfect forwarding is essential for generic functions that accept any argument type, factory functions and wrappers that construct objects in-place, and avoiding unnecessary copies in template code. When combined with variadic templates, it enables functions to forward any number of arguments perfectly.
\begin{lstlisting}
template<typename... Args>
void emplace(Args&&... args) {
    // Forwards all arguments, preserving their value categories
    construct(std::forward<Args>(args)...);
}
\end{lstlisting}

\section{Lvalues and Rvalues}
In C++, every expression has both a type and a \idx{value category}. The two most important value categories are \idx{lvalue} and \idx{rvalue}. An \idx{lvalue} (``locator value'') is an expression that refers to a persistent object in memory - it has an address and can be assigned to. An \idx{rvalue} (``read value'') is a temporary value that does not persist beyond the expression that creates it - it can be read but not assigned to.
\begin{lstlisting}
int x = 10;
int y = 20;

x = y;       // x is an lvalue (has an address, can be assigned to).
             // y is also an lvalue (used as the source of the value).

x = x + y;   // x on the left is an lvalue.
             // (x + y) is an rvalue (a temporary result, no address).

int& ref = x;    // OK: An lvalue reference can bind to an lvalue.
// int& bad = 5; // ERROR: An lvalue reference cannot bind to an rvalue.

int&& rref = 5;  // OK: An rvalue reference can bind to an rvalue.
rref = 10;       // OK: rref is now an lvalue (it has a name and address).
\end{lstlisting}
Understanding the distinction is essential for \idx{move semantics} and \idx{perfect forwarding}. When an rvalue is assigned to an \idx{rvalue reference} (a kind of \idx{reference} declared with \texttt{\&\&}), it signals that the value is temporary and its resources can be ``stolen'' (moved) rather than copied.

\section{Move Semantics}
Introduced in \idx{C++11}, \idx{move semantics} allow resources (e.g., heap memory, file handles) to be transferred from one object to another rather than copied. This avoids expensive deep copies of temporary objects. A \idx{move constructor} and \idx{move assignment operator} are invoked when the source is an \idx{rvalue}, allowing the destination to ``steal'' the internal pointer and leave the source in a valid but empty state. The \idx{std::move} function casts an lvalue to an rvalue reference, enabling the move.
\begin{lstlisting}
std::string a = "Hello, World!";

// Without std::move: Copies the string data (expensive).
std::string b = a;

// With std::move: Transfers the internal buffer (cheap).
// 'a' is left in a valid but unspecified state (usually empty).
std::string c = std::move(a);
\end{lstlisting}

\section{Virtual Functions and the Vtable}
When a class contains \idx{virtual} functions, the compiler implements \idx{dynamic dispatch} (runtime polymorphism) using a hidden data structure called a \idx{vtable} (virtual method table). Each class with virtual functions gets a single vtable containing pointers to the virtual function implementations for that class. Every instance of that class secretly holds a hidden pointer (the \idx{vptr}) to its class's vtable.
\begin{lstlisting}
class Base {
public:
    virtual void doWork() { std::cout << "Base" << std::endl; }
};

class Derived : public Base {
public:
    void doWork() override { std::cout << "Derived" << std::endl; }
};

int main() {
    Base* obj = new Derived();
    // At runtime, obj->vptr points to Derived's vtable.
    // The vtable points to Derived::doWork.
    obj->doWork(); // Output: Derived.
    delete obj;
    return 0;
}
\end{lstlisting}
The key takeaway is that virtual calls incur a small runtime overhead (two pointer dereferences: one to get the vptr, one to get the function pointer from the vtable) compared to non-virtual calls. A virtual call also prevents the compiler from inlining the function. The \idx{override} keyword (C++11) is recommended to ensure the function actually overrides a base class virtual function, producing a compiler error if the signature does not match.

\section{RAII (Resource Acquisition Is Initialization)}
\idx{RAII} is a core C++ programming idiom where a resource's \idx{lifetime} is tied to the lifetime of an object. The resource (memory, file handle, socket, mutex) is acquired in the object's constructor and released in its destructor. Because C++ guarantees that destructors run when an object goes out of \idx{scope} (even via exceptions), RAII guarantees leak-free resource management without manual cleanup.
\begin{lstlisting}
#include <fstream>
#include <mutex>

void processData() {
    // File is opened in the constructor.
    std::ifstream file("data.txt");
    if (!file) return;

    // Mutex is locked in the constructor.
    std::lock_guard<std::mutex> lock(my_mutex);

    // ... do work ...

    // No manual cleanup needed!
    // 'lock' unlocks the mutex in its destructor when it goes out of scope.
    // 'file' closes the file handle in its destructor.
} // Destructors run here in reverse order of construction.
\end{lstlisting}
\idx{Smart pointers} (see Section on Smart Pointers) are themselves an application of RAII to dynamic memory.

\section{SFINAE (Substitution Failure Is Not An Error)}
\idx{SFINAE} is a C++ language rule that applies during \idx{overload resolution} for templates. If substituting a template parameter fails (e.g., a type does not have a required member), the compiler does not issue an error. Instead, it silently removes that template from the candidate list and continues checking other overloads. It is the mechanism that makes \idx{std::enable\_if\_t} work.
\begin{lstlisting}
#include <iostream>

// This overload is removed via SFINAE if T does not have a 'size()' method.
template<typename T>
auto getSize(const T& val) -> decltype(val.size()) {
    return val.size(); // Valid for std::vector, std::string, etc.
}

// This fallback overload is used when val.size() fails substitution.
template<typename T>
auto getSize(const T& val) -> decltype(sizeof(T)) {
    return sizeof(val); // Falls back to byte size for int, double, etc.
}

int main() {
    std::string s = "hello";
    std::cout << getSize(s) << std::endl;    // Output: 5 (string length).

    int x = 42;
    std::cout << getSize(x) << std::endl;    // Output: 4 (sizeof int).
    return 0;
}
\end{lstlisting}

\section{auto and decltype}
Introduced in \idx{C++11}, \idx{auto} lets the compiler deduce a variable's type from its initializer. \idx{decltype} inspects an expression's type at compile time. Both reduce verbosity, especially with complex iterator or template types, and keep code maintainable when types change.
\begin{lstlisting}
std::map<std::string, std::vector<int>> data;

// auto deduces the complex iterator type.
for (auto it = data.begin(); it != data.end(); ++it) {}

// decltype extracts the type of an expression.
int x = 5;
decltype(x) y = 10; // y is deduced as int.
\end{lstlisting}

\section{constexpr and consteval}
\idx{constexpr} (C++11) asserts that a function or variable can be evaluated at \idx{compile time}. If the inputs are constant expressions, the compiler computes the result during compilation rather than at runtime, inlining the final value directly into the binary.
\idx{consteval} (C++20) is stricter: it forces the function to \emph{only} be evaluated at compile time. If called with runtime values, it produces a compiler error.
\begin{lstlisting}
// Can run at compile time or runtime.
constexpr int square(int x) { return x * x; }

// MUST run at compile time only.
consteval int cube(int x) { return x * x * x; }

int main() {
    int runtime_val = 5;

    int a = square(runtime_val);  // OK: Evaluated at runtime.
    int b = square(5);            // OK: Evaluated at compile time.

    int c = cube(5);              // OK: Evaluated at compile time.
    // int d = cube(runtime_val); // ERROR: consteval requires compile-time input.
    return 0;
}
\end{lstlisting}

\section{nullptr}
Introduced in \idx{C++11}, \idx{nullptr} is a strongly-typed null pointer constant. It replaces the traditional \texttt{NULL} (which is defined as \texttt{0} or \texttt{((void*)0)}). Using \texttt{nullptr} prevents ambiguity in function overload resolution, where \texttt{NULL} or \texttt{0} could be misinterpreted as an integer.
\begin{lstlisting}
void process(int x)   { std::cout << "Integer" << std::endl; }
void process(int* p)  { std::cout << "Pointer" << std::endl; }

int main() {
    process(NULL);      // Ambiguous: Might call process(int).
    process(nullptr);   // Unambiguous: Calls process(int*).
    return 0;
}
\end{lstlisting}

\section{User-Defined Type Conversions}
C++ allows a class to define how it implicitly or explicitly converts to other types. An \idx{implicit conversion} is defined by a non-explicit constructor taking a single argument, or a \idx{conversion operator}. An \idx{explicit conversion} (C++11) requires an explicit cast or construction, preventing accidental silent conversions.
\begin{lstlisting}
class Meter {
    double value;
public:
    // Allow implicit conversion from double to Meter.
    Meter(double v) : value(v) {}

    // Allow explicit conversion from Meter to double.
    explicit operator double() const { return value; }
};

int main() {
    Meter m = 5.5;             // Implicit conversion: double to Meter.
    // double d = m;           // ERROR: 'operator double' is explicit.
    double d = static_cast<double>(m); // OK: Explicit cast required.
    return 0;
}
\end{lstlisting}
